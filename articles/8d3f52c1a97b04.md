# はじめに

## 前回のあらすじ

https://zenn.dev/boykush/articles/11cfc3e1abc563

mise は Dev Tools（asdf のような開発ツール管理）・Environments（direnv のような環境変数管理）・Tasks（make のようなタスクランナー）の 3 つをコンセプトに挙げる CLI ツールです。前回の記事では、brew や zshrc に分散していたマシングローバルな開発環境の設定を mise の設定ファイルへ集約し、CLI ツールのバージョン・環境変数・シェルエイリアス・自作スクリプトを静的管理するようにしました。

その中で初期セットアップスクリプトは、mise install 後に発火する [postinstall hook](https://mise.jdx.dev/hooks.html) から以下を実行する形にしていました。

- mise Registry に含まれない GUI アプリ・フォント等の brew install
- dotfiles リポジトリ内の各ツール設定ファイルを参照するシンボリックリンクの一括作成

要は mise install の1コマンドに、CLI ツールの導入からこれらのセットアップ処理までを相乗りさせ、dotfiles の整備を完結させていた形です。

## 経緯

ありがたいことに前回記事へ継続的に Like をもらっていましたが、 前回記事に関連する機能が多くリリースされたことで dotfiles の移行を進めていました。

関連する機能として、miseにDeclarative machine bootstrapと呼ばれる機能群が[v2026.6.6](https://github.com/jdx/mise/releases/tag/v2026.6.6)で追加され、[v2026.7.4](https://github.com/jdx/mise/releases/tag/v2026.7.4)（リリースタイトルは "Bootstrap goes stable"）でexperimentalを卒業しGAとなりました。

新環境のセットアップを `mise bootstrap` コマンド一発で流せるようにする機能で、前回postinstall hookでワークフロー化していたセットアップ処理を、まるごと専用の公式機能に置き換えられるようになりました。せっかくなので移行し、前回の続編として残します。

## 本記事のスコープ

miseは直近でサプライチェーン攻撃対策となるような機能（lockfileやminimum_release_age、disable_backends等）の拡充にも力を入れていますが、本記事では扱いません。mise本体の導入をスクリプト化する `mise generate bootstrap` も同様です。いずれも業務での実践として別記事で紹介したいと思っています。本記事は「mise導入済みのマシンで、セットアップをmise bootstrapに集約する」話に絞ります。なお似たような関心として、CLI ツールのバージョン固定と Renovate による更新については[前回記事のDev Tools管理移行の節](https://zenn.dev/boykush/articles/11cfc3e1abc563#cli%E3%83%84%E3%83%BC%E3%83%AB%E3%81%AEbrew-%3Emise-dev-tools%E7%AE%A1%E7%90%86%E7%A7%BB%E8%A1%8C)で触れています。

## 成果物

引き続き、以下のdotfilesリポジトリです

https://github.com/boykush/dotfiles

新しいマシンでのセットアップは以下の2コマンドになりました

```bash
git clone git@github.com:boykush/dotfiles.git ~/dotfiles
cd ~/dotfiles && mise bootstrap
```

前回あった `setup-mise.sh` と `mise/hooks/postinstall.sh` はリポジトリから消え、 `mise/config.toml` の宣言に置き換わっています。ついでに `.zshrc` まで消えていますが、それぞれどこへ行ったのかを本編で紹介します。

# mise bootstrapとは

https://mise.jdx.dev/bootstrap.html

`mise bootstrap` は、設定ファイルの宣言に向けてマシンを収束させるセットアップコマンドです。実行すると以下のようなステップが順に流れ、それぞれ対応するセクションに宣言した内容を適用します。

1. パッケージのインストール（`[bootstrap.packages]`）：brew-cask 等のパッケージマネージャを通じたアプリケーション導入
2. Git リポジトリの同期（`[bootstrap.repos]`）：リモートにある dotfiles リポジトリ等との同期
3. dotfiles の適用（`[dotfiles]`）：シンボリックリンク等による設定ファイルの配置
4. macOS 設定の反映（`[bootstrap.macos.defaults]`）：defaults の書き込み
5. 開発ツールのインストール（`[tools]`）：mise install 相当

※ この他にもプラグイン導入やシェル有効化などのステップがありますが、私が未実践のため省いています。記事の最後に改めて紹介します。

各ステップは宣言済みの状態へ収束する挙動のため、すでに適用済みの項目はスキップされ、何度実行しても安全です。新しいマシンではまとめて一発実行し、運用中は状態確認や部分実行を組み合わせて使います。

```bash
mise bootstrap                 # 全ステップを実行
mise bootstrap status          # 宣言と実マシンの差分を確認
mise bootstrap --dry-run       # 実行内容のプレビュー
mise bootstrap --only packages # 特定ステップのみ実行
```

次章から、これらのステップへの移行内容を順に紹介します。なお `[tools]` の CLI ツールインストールもステップに含まれるため、前回のように mise install を個別に実行する必要はなくなりました。

# 各ステップへの移行内容

## [bootstrap.packages] GUIアプリ・フォントのインストール

https://mise.jdx.dev/bootstrap/packages/

前回は mise Registry に含まれない GUI アプリやフォントを、postinstall スクリプト内の brew install ループで導入していました。この部分を `[bootstrap.packages]` セクションへの宣言に置き換えました。

**サンプルコード:**
```toml:dotfiles/mise/config.toml
[bootstrap.packages]
"brew-cask:arc"       = "latest"
"brew-cask:claude"    = "latest"
"brew-cask:codex-app" = "latest"
"brew-cask:ghostty"   = "latest"
# フォント（ghostty 主フォント）
"brew-cask:font-hack-nerd-font" = "latest"
```

brew-cask マネージャへの宣言により、`mise bootstrap` のパッケージステップでインストールされます。CLI ツールを管理する `[tools]` と違い mise install では導入されず、bootstrap 実行時のみ適用されるのが使い分けです。

一旦バージョンは latest 固定でGUIアプリケーション側で更新する想定をしており、バージョン固定等は追って検討予定です。

なお brew-cask マネージャは、mise 組み込みのインストーラーが cask のメタデータから直接インストールする仕組みで、Homebrew 本体を必要としません。手動での brew install どころか、Homebrew への依存自体がなくなった形です。

## [bootstrap.repos] dotfilesリポジトリの同期

https://mise.jdx.dev/bootstrap/repos.html

これまでローカルの dotfiles リポジトリを最新に保つ作業は、都度手動 git pull で行っていました。`[bootstrap.repos]` に Git リポジトリを宣言することで、この同期も bootstrap のステップに含められます。

**サンプルコード:**
```toml:dotfiles/mise/config.toml
[bootstrap.repos]
"~/dotfiles" = { url = "git@github.com:boykush/dotfiles.git", ref = "main" }
```

配置先が未 clone であれば取得し、clone 済みであれば ref に指定した main へ追従します。ローカルに未コミットの変更がある場合や origin が一致しない場合は、上書きせず失敗してくれる安全側の挙動です。

新しいマシンでは設定ファイル自体がリポジトリ内にあるため git clone から始めることになりますが、以降は bootstrap を実行するたびに dotfiles が最新化されるようになりました。このステップは dotfiles 適用より前に走るため、後続のステップは常に最新の宣言を参照します。

## [dotfiles] 設定ファイルの配置

https://mise.jdx.dev/dotfiles.html

dotfiles の適用では symlink と block の 2 つのモードを使い分けているため、順に紹介します。

### シンボリックリンクの宣言管理

前回、各ツールの設定ファイルは postinstall スクリプト内の ln -sf でシンボリックリンクを張っていました。この部分を `[dotfiles]` セクションの宣言に置き換えました。

**Before:**
```bash:dotfiles/mise/hooks/postinstall.sh（前回）
# Create symlinks
ln -sf "$dotfiles/.gitconfig" ~/.gitconfig
ln -sf "$dotfiles/git" ~/.config/git
ln -sf "$dotfiles/zellij" ~/.config/zellij
ln -sf "$dotfiles/wezterm" ~/.config/wezterm
ln -sf "$dotfiles/nvim" ~/.config/nvim
```

**After:**
```toml:dotfiles/mise/config.toml
[dotfiles]
# mise 設定自身（グローバル設定の実体）
"~/.config/mise" = "~/dotfiles/mise"
# ホーム直下
"~/.gitconfig" = "~/dotfiles/.gitconfig"
# ~/.config 配下（ディレクトリごと）
"~/.config/helix" = "~/dotfiles/helix"
...
```

キーが配置先、値がリポジトリ内のソースパスで、各エントリがシンボリックリンクとして張られます。

### zshrc初期化のblockモード管理

前回、.zshrc はリポジトリ内のファイルとして持ち、シンボリックリンクで配置していました。mise への移行が進んだ結果、その中身は実質ツール初期化の eval 3 行だけになっていました。

**Before:**
```zsh:dotfiles/.zshrc（前回）
eval "$(mise activate zsh)"
eval "$(zoxide init zsh)"
eval "$(starship init zsh)"
```

ここまで来るとファイルごと管理するまでもないため、この 3 行を block として宣言する形にし、.zshrc の symlink とリポジトリ内のファイル自体を不要にしました。

**After:**
```toml:dotfiles/mise/config.toml
[dotfiles]
"~/.zshrc/activate" = { block = 'eval "$(mise activate zsh)"' }
"~/.zshrc/zoxide"   = { block = 'eval "$(zoxide init zsh)"' }
"~/.zshrc/starship" = { block = 'eval "$(starship init zsh)"' }
```

キーは「対象ファイルのパス/ブロック名」の形式です。適用すると対象ファイルへマーカーコメント付きのブロックが書き込まれ、以降はマーカー間だけを mise が管理します。

```zsh:~/.zshrc（適用結果のイメージ）
# >>> mise:activate >>> managed by mise — do not edit between markers
eval "$(mise activate zsh)"
# <<< mise:activate <<<
# >>> mise:zoxide >>> managed by mise — do not edit between markers
eval "$(zoxide init zsh)"
# <<< mise:zoxide <<<
...
```

マーカーの外には一切触れないため、mise が所有していないファイルへ安全に相乗りできます。また現時点の実装では宣言順に追記されるため、mise のツールを PATH に通す activate を先頭に置き、zoxide・starship の初期化をその後に続ける順序を保てます。

なお symlink と block の他にも、symlink-each・copy・template や行単位編集の line といったモードがあるようですが、私は未実践のため名前の紹介に留めます。

## [bootstrap.macos.defaults] macOSシステム設定の反映

https://mise.jdx.dev/bootstrap/macos-defaults.html

キーリピート速度や Dock の挙動といった macOS のシステム設定も、mise では `[bootstrap.macos.defaults]` への宣言として管理でき、bootstrap の macOS ステップで値の型に応じた `defaults write` が適用されます。

**サンプルコード:**
```toml:dotfiles/mise/config.toml
[bootstrap.macos.defaults.NSGlobalDomain]
KeyRepeat = 2.0         # キーリピート速度: 最速
InitialKeyRepeat = 15.0 # リピート開始までの遅延: 最短
# 長押しでアクセント記号ピッカーを出さずキーリピートさせる
ApplePressAndHoldEnabled = false

[bootstrap.macos.defaults."com.apple.dock"]
autohide = true
```

私はこれまでシステム設定を手動で行っていて宣言管理は今回が初めてのため、まずはキーボードリピートと Dock の最小セットから始めています。

## bootstrap statusによる健全性チェック

セットアップが宣言になったことで、あるべき状態と実マシンの乖離を機械的に検証できるようになりました。各ステップの status サブコマンドがこれを担います。

```bash
mise bootstrap status                    # 全ステップの状態を確認
mise bootstrap dotfiles status --missing # 乖離があれば exit 1
```

これまでの postinstall スクリプト運用は「実行する」ことしかできず、ソースファイルの移動や削除で生じるシンボリックリンクのリンク切れに気づく仕組みがありませんでした。status は各エントリの未適用・ソース消失・差分を検知してくれるため、ローカルの健全性チェックとして有効です。

さらに CI に載せれば、新環境セットアップが壊れていないかの継続的なテストにもなります。私の dotfiles では GitHub Actions の macOS ランナーで bootstrap を実適用し、status で収束を検証しています。CI 向きでない GUI アプリの packages と SSH 前提の repos は `--skip` で外しています。

**サンプルコード:**
```yaml:.github/workflows/mise-bootstrap.yml（抜粋）
- name: Bootstrap (dotfiles + tools)
  run: cd "$HOME/dotfiles" && mise bootstrap --skip packages,repos --force-dotfiles

- name: Verify convergence
  run: |
    cd "$HOME/dotfiles"
    mise bootstrap dotfiles status --missing
    mise bootstrap macos defaults status --missing
```

# まとめ

本記事で紹介した以外にも、bootstrap には以下のようなステップが用意されています。

- `[bootstrap.plugins]`：`[bootstrap.packages]` で使えるマネージャを拡張するプラグイン（VS Code 拡張等）の事前導入
- `[bootstrap.mise_shell_activate]`：.zshrc のようなシェル設定ファイルへの mise activate 行の追記
- `[bootstrap.macos.launchd.agents]` / `[bootstrap.linux.systemd.units]`：macOS / Linux の常駐サービスの登録・起動
- `[bootstrap.user]`：ログインシェルの変更（chsh 相当）
- `[bootstrap.hooks]`：主要ステップの前後への任意スクリプトの差し込み（pre-packages 等）
- bootstrap タスク：bootstrap という名前の mise Task を定義しておくと仕上げに実行

中でもシェルへの activate 追記を担う `[bootstrap.mise_shell_activate]` は導入を検討したのですが、zoxide・starship の初期化も同じ場所で順序込みに管理したかったため、活用しきれず `[dotfiles]` の block 管理へ寄せた経緯があります。

スコープ外にしたサプライチェーン攻撃対策となるような機能含め、痒いところに手が届く機能がすごいスピードで追加されておりすっかり mise のファンになりました。今回を機に Sponsors にも登録しています。みなさんも良いツール管理ライフを！
